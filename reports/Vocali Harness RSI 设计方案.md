# Vocali Harness + RSI 设计方案（v0.1，待审）

日期：2026-11-20　｜　对象：VoiceLocater（Vocali）Mac 版的识别、说话人归属与翻译流水线

---

## 0. 需求确认（问答结论）

| 项 | 结论 | 对设计的影响 |
|---|---|---|
| 目标 | 产品和论文都要，**产品优先** | 最终裁判是自采真实场景数据；公开基准只用于搜索和对照 |
| 产品形态 | Vocali：Mac 本机、**实时**字幕、匿名说话人标签、整句翻译 | 每个 harness 动作都必须是流式可执行的 |
| 设备 | **只管 Mac**（Qwen3-ASR 1.7B + Audar Turbo，MLX 8-bit）；本期只做**单个远场麦**（近场多麦没有测试环境，推迟） | 远场重叠时没有"换输入"可用 |
| 语种 | 阿拉伯语（**海湾方言 + MSA**）、英语、中文；**整场基本单一语种**，但**事先不知道** | 语种可以按"整场"累积判断，比现在的逐句判断强得多 |
| 优化目标 | 识别准确率、说话人归属、**阿→英 / 英→阿**翻译质量 | 适应度是一个向量 |
| 硬约束 | 实时体验（延迟、改写、算力）**不能比现在差** | 所有候选先过约束检查，再比较准确率 |
| 可改范围 | **只改模型以外的东西**（阈值、代码、提示词、词表、后处理），不动权重 | RSI 只做 L0–L2 三层，不做 L3 |
| 词表来源 | 用户会前输入、从会议材料自动提取、固定行业词库，三种都有 | 需要按场次检索词表，并评估专业词识别 |
| 算力 | 大规模搜索在 JUBAIL；**只有 macmini** 可以存放评测音频并做真机验证 | 需要一个能在 JUBAIL 上运行的"数字孪生"，并定期在 macmini 上校准它 |
| 自采数据 | 每个语种 1–3 小时，组内自行录制和标注 | 只够做锚点集和最终测试，不够用于搜索 |

## 1. 现状：Vocali 里已有的 harness

读代码确认的流水线（`VoiceLocater/Sources`）：

```
麦克风（Mac 内置 3 通道，混成单声道）→ 16 kHz → Silero VAD
  ├─ NemotronStream：Nemotron 3 流式说话人分离（Core ML），每 80 ms 给出每人说话概率
  ├─ Transcriber：按 VAD 切句，每 0.6/0.9 s 对当前句的已有前缀重解码一次（partial），句末出 final
  │     └─ RoutedDecoder（auto-qwen-audar）：Qwen 判断语种、Audar 转写
  ├─ ActivityTracker（on 0.5 / off 0.35 / confirm 0.6 / hold 0.24）：判断谁在说话
  ├─ TranscriptAligner：按时间把每个词分给当时在说话的人
  ├─ VoiceProfiles（CAM++，accept 0.55 / keep 0.42 / learn 0.65）：匹配已注册的人
  └─ CaptionTranslator：每句说完后用 HY-MT / Hy-MT2 / Index 整句翻译，上下文是前 2 句
```

当前的路由规则（`RoutedDecoder.swift`）：

- 证据 = Qwen 的 P(ar) 换算成对数几率，加上说话人先验（这个人上一句的语种，权重 1.0；否则用上一句的语种，权重 0.5），再加上文字体系项（Qwen 输出中阿拉伯字母占比 ≥ 0.6 加 1，≤ 0.1 减 1）。
- 证据 ≥ `margin` 1.5，且在 `decideWithin` 3 s 以内，就切到 Audar，用 Audar 重解码这一句。
- 规则从不提前判定"不是阿拉伯语"；超过 3 s 仍未判定的句子留在 Qwen。

已有的评测工具：

- `tools/replay_eval.sh` 和 `tools/streaming_eval.py`：把音频文件当作实时输入回放，统计 updates/min、NE（normalised erasure，被擦掉的文字占最终文字的比例）、big rewrites（一次删掉 ≥ 4 个词的大改写）、word lag、first lag、final lag、MER、chrF。
- `tools/arabic_bench`：阿拉伯语 ASR 对比（FLEURS ar_eg、MIXAT）。
- 可调参数大多写死成 `static let` 或 `var` 常量，散落在 6 个文件里；另有若干 `VOCALI_*` 环境变量开关。

**结论：** Vocali 已经是一个手工维护的 harness，并且有了回放评测。缺的是三样东西：

1. 能大规模、可复现运行的离线评测。
2. 一个改不了的评测器和固定的数据切分。
3. 一个"提出改动 → 评测 → 晋升"的循环。

本方案就补这三样。

## 2. 需求带来的四个关键判断

1. **整场单语种是最大的杠杆。**
   - 现在的先验只看"这个人上一句"和"上一句"，每句仍要从零累积证据。在 3 s 窗口里，前 1–2 s 显示的是 Qwen 的文字，切换后会被整段替换。
   - 改成**整场累积的语种后验**之后：开场前几句就能锁定语种，后面的句子从第一个 partial 起直接用对的模型。准确率、改写次数和算力会同时改善（阿拉伯语句子少一次 Qwen 解码）。
   - 风险是开场判错后整场都错，所以需要"后验持续反对时解锁"的规则。具体参数交给 RSI 搜索。

2. **远场单麦的重叠没有"换输入"可做。**
   - 只改模型以外的东西、且算力不能增加，意味着不能加分离模型。
   - harness 在重叠上能做的只有三件事：
     - 在 Nemotron 报告说话人切换处切句，避免两个人的话被拼成一句；
     - 重叠区内的词暂缓定稿，等重叠结束后再做 final；
     - 改进 TranscriptAligner 的归属规则。
   - 实验 A、B、C 已经量化了这块的上限（远场重叠时有 28% 的语句会转写成另一个人的话）。产品上能挽回的是其中"归属错"的部分，"内容错"的部分基本挽回不了。

3. **近场麦场景的主要问题是串音。**
   - 每人一支麦时，旁边人的声音会漏进来，表现为同一句话在两支麦里各出一次，或者被分给错的人。
   - 对应的 harness 动作是按通道能量比判定说话人，并抑制串音重复。
   - **这条依赖 Vocali 能否同时采集多路麦克风输入**（代码里有 `Microphone.swift` 和 `docs/research/multichannel-input.md`，尚未确认）。见 §10 的待确认项。

4. **翻译只能靠上下文和术语来提升。**
   - 不能改翻译模型，所以 RSI 只能改送进模型的东西：前文窗口的大小和来源（同一说话人，还是所有人）、术语表注入（HY-MT 系列有术语干预模板）、句子边界（何时把半句送去翻译）。
   - 翻译质量必须按端到端衡量，也就是"语音 → ASR → MT"。ASR 的改动可能让翻译变差，反过来也一样。

## 3. 总体架构

```
            ┌──────────────── JUBAIL（搜索）────────────────┐        ┌──── macmini（真机）────┐
 公开语料 → │ ① 解码缓存   Qwen3-1.7B / Audar（PyTorch bf16） │        │ Vocali 回放             │
 合成会话 → │    按 Vocali 的 partial 调度，对每个前缀解码一次  │        │ voice-locater stream    │
            │    存：文本、token 置信度、P(zh/en/ar)           │        │ --input-file            │
            │ ② 分离缓存   Nemotron 3 流式分离（80 ms 概率）    │        │                         │
            │ ③ 数字孪生   Python 版策略层（读 HarnessConfig） │◀─校准──│ 锚点集（自采 + 公开小样）│
            │    路由 / 切句 / 归属 / 翻译触发，在 CPU 上重放   │──候选─▶│ 晋升前复测               │
            │ ④ 锁定评测器  WER/CER/cpWER/chrF/COMET/时延代理   │        └─────────────────────────┘
            │ ⑤ 提议者     L0 Optuna；L1/L2 编码 agent        │
            └───────────────────────────────────────────────┘
                      ▲  git（代码、配置、轨迹摘要）  ▼
                  本地笔记本：编码 agent 改孪生和 Swift 代码（不存放任何音频）
```

### 3.1 HarnessConfig：把所有旋钮集中到一个文件

- 把散落在各处的常量（§5.1）收进 `HarnessConfig.json`。Swift 端启动时读取它，缺省值等于现在的常量，因此行为不变；Python 孪生读同一个文件。
- 这一步本身不改变任何行为，但它是 L0 搜索能真正落到产品上的前提。

### 3.2 解码缓存

- 模型的输出只取决于"哪段音频、哪个模型、什么语言参数、什么上下文"，与策略无关。因此在 JUBAIL 上按 Vocali 的 partial 调度，对每句的每个前缀长度各解码一次并缓存：
  - Qwen 在语种限定为 zh/en/ar 时：输出文本和 P(语种)；
  - Audar 在强制阿拉伯语时：输出文本。
- 之后孪生重放任意阈值组合，都只是查表。
- **注意：** 切句策略一变，前缀边界就会变。所以缓存要按"音频起点 + 0.1 s 粒度的终点"建索引；候选策略查不到的前缀再补解码（懒加载）。
- 提示词或词表（L2）改变时，缓存键要包含上下文串的哈希。

### 3.3 数字孪生与真机校准

- 孪生只重写**策略层**：RoutedDecoder 的证据与决策、Transcriber 的切句与定稿、ActivityTracker、TranscriptAligner、CaptionTranslator 的触发和上下文。
- 模型数值来自缓存（bf16），而真机是 MLX 8-bit，两者会有偏差。
- **一致性检验**（每次大版本、以及每月一次，在 macmini 锚点集上）：
  - 路由决策一致率 ≥ 95%；
  - 各语种 WER/CER 差值 ≤ 0.5 个点（绝对值）；
  - 时延代理（§4.3）与真机实测的秩相关 ≥ 0.8。
- 达不到时，先修孪生，或者把对精度敏感的阈值（如 `margin`）留到 macmini 上做最后的小网格微调。

### 3.4 轨迹

- 孪生和真机都按同一份 NDJSON schema 输出每次 pass 的完整记录：
  - 时间、句子 ID、说话人概率、P(ar)、证据各分项、决策和原因、所用引擎；
  - 文本、是否定稿、送翻译的时刻、上下文、译文。
- 真机这边要给 `voice-locater stream --json` 补充这些字段（目前只有 transcript 和 activity）。
- 轨迹是 L1 提议者读的"原始错误材料"，只把搜索集的轨迹给它。

## 4. 锁定评测器

评测代码放在只读目录，用校验和锁定。孪生和真机共用同一份。

### 4.1 准确率（主目标）

| 指标 | 说明 |
|---|---|
| 英文 WER、中文 CER、阿拉伯语 WER + CER | 阿拉伯语用 N1 归一化（与 127 上的基准一致）；三种语言分开报告，不取平均 |
| SMR（文字体系不匹配率） | 输出文字体系与参考语种不符的语句占比，用来抓"误送 Audar 后输出翻译文本"的问题 |
| 路由准确率、首次切换时刻、被替换的文字长度 | 用来解释准确率的变化 |
| B-WER / U-WER | 词表内的词和词表外的词分别计算 WER，评估词表的效果 |

### 4.2 说话人归属（主目标）

- **cpWER / tcpWER**（MeetEval；匿名标签按最优置换匹配）。
- **Δcp** = cpWER 减去不计说话人的 WER，用来单独衡量归属错误。
- **DER**，以及说话人数误差。

### 4.3 翻译（主目标，仅阿→英、英→阿）

- **端到端**的 chrF++ 和 COMET（JUBAIL 上的 COMET 模型）；对照项是 oracle 转写的翻译，用来区分 ASR 带来的损失和 MT 本身的损失。
- 术语准确率：词表里的术语在译文中是否按指定方式翻译。

### 4.4 实时体验（硬约束，不能比基线差）

| 约束 | 孪生里怎么算 | 真机怎么测 |
|---|---|---|
| first lag / final lag / word lag | 按 partial 调度和缓存中的解码时长（用真机测得的每秒音频解码时间换算）模拟 | `streaming_eval.py` |
| NE、big rewrites/min、updates/min | 直接从模拟出的字幕序列计算 | 同上 |
| 算力 | 每秒音频的解码音频秒数，按模型分别计算，再加翻译调用次数 | macmini 上实测 RTF 和功耗 |

- 判定规则：用 bootstrap 求 95% 置信区间。差值的上界不超过基线的 2%（噪声容限，可调）才算"不变差"。

### 4.5 晋升规则

候选版本要全部满足以下条件，才会被保留：

1. 选择集上**所有**约束都满足。
2. 主目标里至少一项改善，且其余各项不显著变差（帕累托意义下）；删除率和空输出率不能上升。
3. **跨语种门：** 阿、英、中三种语言各自不显著退化。
4. diff 审计通过：没有出现片段 ID 或文件名，没有修改评测器目录，没有硬编码的参考文本。

## 5. RSI 三层设计（只改模型以外的东西）

### 5.1 L0：参数搜索

| 模块 | 参数（当前值） | 备注 |
|---|---|---|
| RoutedDecoder | margin 1.5；decideWithin 3.0；speakerWeight 1.0；recentWeight 0.5；scriptWeight 1.0；文字体系阈值 0.6 / 0.1 | 新增 sessionWeight、解锁阈值（见 L1-a） |
| Transcriber | partialInterval 0.6 / 0.9；firstPartialAfter 0.8；lockAfter 2.0；switchConfidence 0.75；maximumUtterance 12；commitMargin 0.8 | 与时延约束强相关 |
| ActivityTracker | on 0.5；off 0.35；confirm 0.6；hold 0.24 | 影响归属 |
| VoiceProfiles | accept 0.55；keep 0.42；learn 0.65 | 只影响具名匹配，优先级低 |
| CaptionTranslator | 前文 2 句；同一说话人还是所有人；翻译触发时机 | 影响翻译 |

- **方法：** Optuna 多目标搜索（带约束的 TPE 或 NSGA-II），在缓存上重放，每次试验只用 CPU。
- **规模：** 每个模块组先做敏感度分析，再联合搜索。总计约几千次试验，CPU 作业数组几小时就能跑完。
- **产出：** 一个候选 HarnessConfig，以及它在选择集上的帕累托前沿。

### 5.2 L1：代码搜索（编码 agent 改策略代码）

**提议者：** 本地笔记本上的编码 agent（Claude Code），沿用现有的 git 流程。

- 它读搜索集的轨迹摘要和错误样例，改 Python 孪生里的策略模块，push 到 git。
- JUBAIL pull 后用 sbatch 跑搜索集和选择集，结果和轨迹摘要再 rsync 回本地。

**晋升后的落地流程：**

1. 把改动移植到 Swift。
2. 用共享的轨迹 fixture 做对等测试：同一份输入，Swift 和 Python 必须给出相同的决策。
3. 在 macmini 锚点开发集上复测。

**首批候选**（人工写好种子，再交给 agent 变异）：

- **a. 整场语种后验：**
  - 对整场累积对数几率，加入证据时按时间衰减。
  - 后验超过锁定阈值，就从下一句的第一个 pass 起直接用目标引擎。
  - 连续 k 句的证据都反向，就解锁。
- **b. 说话人切换处切句：** Nemotron 的说话人概率出现交替时强制断句，避免两个人的话被拼成一句、只归给一个人。
- **c. 重叠区暂缓定稿：** 两人以上同时活跃的区间里，词不定稿；final 等到重叠结束后再出。约束：final lag 不能超标。
- **d. 归属规则：** 一个词跨越说话人切换点时，从"按词中点归属"改成按说话人概率积分归属；backchannel（"嗯""对"之类的附和）单独处理。
- **e. 翻译签名回退：** 后验判断是中文或英文，Audar 却输出了阿拉伯文时，丢弃 Audar 的结果，回退到 Qwen。
- **f. 近场多麦串音抑制：** 按通道能量比判定说话人，并去掉同一时段在两支麦里各出一次的重复文本（前提是 Vocali 支持多路输入）。
- **g. 翻译分段：** 长句按标点或停顿切开再送翻译；前文窗口只取同一说话人的句子。

### 5.3 L2：上下文搜索（提示词、词表、术语）

**ASR 上下文**（现在只传参会者名字）：

- 搜索三件事：
  - 上下文串的格式（纯词列表，还是一句话描述加词列表）；
  - 每场取多少个词（k）和排序方式；
  - 三种来源（用户输入、材料提取、行业词库）的合并策略。
- 行业词库可能有上千个词，不能全部塞进上下文，需要按本场主题检索 top-k。检索器可以用嵌入或 BM25，选哪种也交给搜索。
- **Audar 对上下文的反应未知**，要单独测：它是否用到了词表，会不会因此产生幻觉。

**纠错规则记忆**（Voice Memory 的思路，但不能增加模型调用）：只允许用便宜的规则，比如词表的音近替换、高频错误替换表。规则来自搜索集，要在选择集上验证不伤害其他文字。

**翻译术语注入：**

- 搜索 HY-MT 的术语干预模板写法，以及哪些术语需要注入。
- 用术语准确率和 COMET 联合评估。

**词表评测数据：**

- **公开数据：** LibriSpeech 的偏置词表（英文，含干扰词）。
- **合成：** 从选择集各场次的参考文本里抽稀有命名实体，再混入大量干扰词。只用于搜索。
- **最终：** 自采数据录制时一并收集会议材料，词表只从材料中提取，不从转写中提取。

## 6. 数据：来源、切分和存放位置

### 6.1 搜索集与选择集（全部在 JUBAIL）

| 用途 | 搜索集 | 选择集 |
|---|---|---|
| 英语会议（远场 / 近场） | NOTSOFAR 约 45 场（sdm + ihm） | NOTSOFAR 另外约 40 场 |
| 英语重叠 | LibriCSS OV10–30，Remix | LibriCSS OV40 |
| 中文会议 | AliMeeting 一半场次 | AliMeeting 另一半 |
| 阿拉伯语（海湾 + MSA） | SADA、MGB-2 等按说话人切出的一半；**合成阿语会话**（见下） | 另一半；FLEURS-ar |
| 语种负样本 | FLEURS-en/zh、ASCEND 一半 | 另一半 |
| 翻译 | FLEURS en_us ↔ ar_eg 平行句的一半（同一句话有阿、英两种录音和文本） | 另一半 |

- 马格里布、埃及等方言不属于目标用户，只作为鲁棒性观察项，不参与晋升判断。
- **合成阿语会话：** 公开数据里没有阿拉伯语多人会议。做法：
  - 把同语种、不同说话人的单人语句按轮流发言拼接，并按实验 C 的生成器加入少量重叠和远场化处理；
  - 作用是检验"整场语种后验"和说话人归属在阿拉伯语上的表现；
  - 只用于搜索，不用于选择。

### 6.2 最终测试（任何搜索都不碰）

- **公开数据（JUBAIL）：**
  - NOTSOFAR 剩下的约 44 场；
  - AMI、CHiME-6、DiPCo 全部；
  - 阿拉伯语整套留出 Casablanca-UAE 和 Mixat。
- **自采锚点集（只放在 macmini）：** 每个语种 1–3 小时，切成两份：
  - **锚点开发集（约 1/3）：** 用于孪生校准和人工核对评测器；
  - **锚点测试集（约 2/3）：** 只在发版前跑一次。

### 6.3 自采方案（最小可行）

**场景与设备：**

- 会议室：3–6 人，用 MacBook 内置麦，放在桌面中央。
- 论坛 / 讲座：每人一支近场麦，同时用 MacBook 录一路远场作对照。

**语种：**

- 阿拉伯语以海湾方言为主，加一部分 MSA 讲座。
- 英语、中文各一组。

**每场要收集：**

- 音频：用 Vocali 的 Record 功能录制，保证输入链路与产品一致。
- 会议材料：议程、幻灯片，用于构建词表。
- 参会人数。

**标注：**

- 转写，附说话人和时间戳。
- 阿拉伯语部分附英文翻译，英语部分附阿拉伯语翻译，用于评测翻译。
- 估算：标注人力约为音频时长的 5–10 倍。每个语种 2 小时，总计约 30–60 人时，另加翻译。

**统计功效：**

- 阿拉伯语 2 小时约 1.2 万词，大约能分辨 1–1.5 个点的绝对 WER 差异。
- 因此锚点集只用来做"有没有变差"的把关和最终报告，不用于细粒度调参。

**合规：** 录音前需要知情同意；数据只存放在 macmini。

## 7. 信用分配：先知道余量在哪

在孪生上按顺序替换真值，相邻两级的差值就是该模块的余量：

1. 基线（当前的 HarnessConfig）。
2. 语种换成真值（整场语种已知）：衡量路由的余量。
3. 切句换成真值（参考时间戳）：衡量 VAD 和切句的余量。
4. 说话人归属换成真值：衡量 Nemotron 加 Aligner 的余量。
5. 翻译输入换成参考转写：衡量 ASR 对翻译的影响。

RSI 的预算按余量分配。根据已有结果，我的预期如下（**需要基线来验证**）：

- 阿拉伯语场景里，"语种"这一级的余量最大（Audar 和 Qwen 相差 5–15 个点）。
- 远场英文场景里，"归属"和"切句"的余量大于"语种"。

## 8. 防作弊与防过拟合

- **空输出换指标：** 对重叠段输出空串可以减少归属错误，所以删除率和覆盖率必须作为约束一起看。
- **延后决策换准确率：** decideWithin 和定稿延迟都受时延约束限制，不能只看准确率。
- **正字法套利：** 归一化器锁定在评测器目录里，提议者不能修改；阿拉伯语同时报告 WER 和 CER。
- **词表泄漏：** 最终评测的词表只来自会议材料；diff 审计拦截任何片段 ID 或参考文本。
- **孪生过拟合：** 孪生上的收益在锚点开发集上至少要保留一半，否则说明孪生与真机不一致，应该暂停晋升、先修孪生。
- **收益饱和：** 文献里自改进系统都会在几十轮内饱和。按"一次性台阶"规划：L0 一次，L1 约 2–3 轮，L2 一次。不要期待持续复利。

## 10. 已拍板的事项（2026-11-20）

1. **近场多麦：** 目前没有多路麦克风的测试环境，因此本期**只做单个远场麦**。L1-f（串音抑制）和"近场麦场景"推迟，等有了采集环境再加。自采数据仍按单麦（MacBook 内置麦）录制。
2. **Nemotron 能在 JUBAIL 上跑。** 调查结论如下：
   - **模型：** Vocali 用的是 `nvidia/Nemotron-3-Diarization`，约 1 亿参数，最多 8 人的流式 Sortformer。FluidAudio 只是把它转成了 Core ML，产品用的是 `low` 预设（chunk 9、right context 4、fifo 264、spkcache 264、update period 222，延迟约 1.04 s）。
   - **PyTorch 版本：** HF 上同时公开了 `.nemo`（199 MB）和 `model.safetensors`。Python 里用 NeMo 的 `SortformerEncLabelModel` 加载，按上面的预设设置 `sortformer_modules`，就能复现产品的流式行为；也可以用 Transformers 的 `set_streaming_mode("low_latency")`。
   - **许可：** OpenMDW 1.1，模型卡写明可商用。
   - **与真机的一致性：** FluidInference 报告，导出包装在 torch 中误差为 0，Core ML fp16 的说话人概率误差在 1.9e-4 以内。AMI MHM 上的 DER：Core ML `low` 为 9.75，官方 bf16 为 9.48，差约 0.25，足够用作孪生。
   - **环境：** JUBAIL 现有环境是 Python 3.12 加 torch 2.9.1，满足要求，但还没装 NeMo。M0 要用一个 Slurm 作业装 `nemo-toolkit[asr]`（不在登录节点上装）。
   - **风险：** 训练数据包括 AMI、ICSI、NOTSOFAR、AliMeeting、DiPCo、AISHELL-4 等会议数据，以及中文和印度语言，**但没有阿拉伯语**。所以阿拉伯语的说话人归属必须单独评测，只能先用合成阿语会话，最终以自采数据为准。另外 `low` 预设的说话人计数准确率（SCA）只有 75.0%（Core ML 仓库给的 AMI 数字），低于高延迟预设的 93.8%。说话人数估错会直接造成归属错误，这是 M1 余量分析要重点看的地方。
   - **注意：** 官方 DER 用的是强制对齐生成的参考标签，与我们的参考标签不能直接比较，必须用我们自己的评测器重新测。
3. **硬约束的噪声容限：** 定为基线的 2%。
4. **翻译模型：** 按场景选。生活化场景用 Hy-MT2，标准正式场景用 Index-Translate。因此：
   - 两个模型都进入评测，指标分别报告；
   - "模型选择"作为 HarnessConfig 里的一个按场景配置项。将来可以让 L1 学一个自动选择器（例如按场景类型或句子语体），但前提是不增加翻译调用次数；
   - 提示词搜索按模型分开做，因为两者的模板不同。
   - 翻译评测集需要标注场景类型，FLEURS 属于标准朗读语体。自采数据要同时覆盖生活化和正式两类。
5. **代码管理：** VoiceLocater 原先未提交的修改已提交到 `main`（`e504c3d`）。之后的改进都在 **`harness-rsi`** 分支上进行（已创建并切换）。
